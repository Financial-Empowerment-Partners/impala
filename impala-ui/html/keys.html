Bridge Keys

Provider credentials and custodial Stellar seeds. Imports add by default; replacing anything already in effect needs an explicit confirmation.

Before you use this page
  • A provider credential is spend authority. Replenishment sends real reserve XLM to the pay-in address the active Changelly account names, so whoever controls these credentials chooses a counterparty the bridge pays.
  • Confirmation stops mistakes, not attackers. Every check here is defeated by one admin token. It exists so you do not replace the wrong thing, and so two operators do not clobber each other.
  • Nothing takes effect until a rolling restart. Credentials are resolved once per process, so all instances switch together rather than drifting apart.
  • Pasting a key into a browser exposes it to the browser — extensions, autofill, session restore, and anything reading this page's memory. impalactl keys import reads secrets from a file, stdin, or a no-echo prompt and is the safer surface.
  • Revoking here does not revoke at the provider. If a key is compromised, revoke it at the provider first.

Full detail: docs/runbooks/import-keys.md.

This bridge runs with KEY_IMPORT_ENABLED=false, so provider credentials come from the deployment configuration and these endpoints refuse. Anything already stored is shown below but is not in use.

Custodial Stellar seeds

Provision a seed the bridge generates itself, or bring an existing one under custody. The conversion-reserve account is generate-only: an imported reserve seed would leave the pool’s signing key in a person’s hands.

History

Every stored version, newest first. Superseded versions stay decryptable for a bounded overlap so in-flight webhooks still verify, then are scrubbed; revoked ones are scrubbed at once.

SEP-10 signing key (card sign-in)

The bridge’s SEP-10 endpoint signs each Stellar Web Authentication challenge with this key, and a card answers with the Stellar key it holds. A challenge signed by a registered card’s Stellar key yields the same session as card sign-in with SIGN_AUTH.

  • Enabling SEP-10 is a bridge setting (SEP10_ENABLED=true, then a restart), not something this page does. These controls work either way, so a key can be in service before the endpoint is switched on.
  • A new key is created pending and signs nothing. Activating it schedules it: it takes over after the activation delay (SEP10_KEY_ACTIVATION_DELAY_SECS, 120 s in the design), on every bridge instance at the same instant, and the previous key becomes superseded.
  • Revoking the active key stops SEP-10 sign-in (the endpoint answers 503) until another key is activated and its delay has passed.
  • Never fund a card’s Stellar address. The card signs only SEP-10 challenges and its key cannot be exported, so nothing can ever sign a transaction that spends from that address: anything sent to it is lost.
  • The signing key is generate-only: there is no import, and no response carries more than the public address and the fingerprint. Generating needs key import enabled on the bridge (KEY_IMPORT_ENABLED with a seed-protection backend).
