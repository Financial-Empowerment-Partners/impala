# Test admin-UI SSO locally with OpenBao as the OIDC IdP

Runs the **entire** OIDC SSO path — login button → IdP login → PKCE code
exchange → bridge token exchange → auto-provisioned account + bridge JWTs —
with **no external identity provider**. The local compose stack's OpenBao
(already present as the Transit seed-protection backend) doubles as a full
OIDC identity provider. For testing against a real Okta org instead, see
[`deploy-okta-sso-admin-ui-cloudflare.md`](deploy-okta-sso-admin-ui-cloudflare.md).

**This is a LOCAL DEVELOPMENT setup only** — dev-mode OpenBao (in-memory,
well-known root token), plain-HTTP issuer, and a fixed test user.

---

## 1. What `docker compose up` provisions

The `openbao-init` one-shot in `impala-bridge/docker-compose.yml` bootstraps,
in addition to the Transit seed key:

| Piece | Value |
|---|---|
| Login (userpass) | `testuser` / `testpassword`, entity email `testuser@example.com` |
| Assignment | `impala-admins` — **only** the testuser entity may authorize (not `allow_all`) |
| Scopes | `email` (→ `email` claim from entity metadata), `profile` (→ `preferred_username`) |
| Client | `impala-admin-ui` — **public** PKCE client, redirect `http://localhost:3000/sso-callback.html` |
| Provider | `openbao`, issuer `http://localhost:8200/v1/identity/oidc/provider/openbao` |
| CORS | enabled for `http://localhost:3000` (the browser POSTs the code exchange to OpenBao) |

The client_id is **generated by OpenBao**, so the init container writes the
bridge's provider config to a shared volume as `/bootstrap/sso-config.json`
and the bridge reads it via `CONFIG_FILE` (see the `impala-bridge` service
env). The bridge validates the **id token** (`openbao_token_kind: "id"` —
OpenBao access tokens are opaque batch tokens) and fetches discovery/JWKS via
the container-internal `openbao_internal_issuer_url` (`http://openbao:8200/…`)
while tokens carry the browser-facing issuer — the split-horizon pair of
`{NAME}_INTERNAL_ISSUER_URL` / `{NAME}_ALLOW_HTTP` registry keys.

## 2. Bring the stack up and verify the bridge

```bash
just up    # bridge stack (pg + redis + openbao + bridge) then UI nginx on :3000

docker compose -f impala-bridge/docker-compose.yml logs openbao-init   # "OIDC test IdP ready (client_id …)"
curl -fsS http://localhost:8080/auth/sso/openbao/config | jq
# → { "enabled": true, "client_id": "…",
#     "authorization_endpoint": "http://localhost:8200/ui/vault/identity/oidc/provider/openbao/authorize",
#     "token_endpoint": "http://localhost:8200/v1/identity/oidc/provider/openbao/token", … }
curl -fsS http://localhost:8080/auth/providers   # includes "openbao"
```

The bridge log shows the deliberate warning
`oidc[openbao]: ALLOW_HTTP enabled — accepting plain-HTTP issuer … (LOCAL DEVELOPMENT ONLY)`
followed by `loaded N keys from JWKS` (JWKS fetched via the internal URL).

> **Local routing.** Nginx proxies `/api/testnet/*` and `/api/mainnet/*` to
> per-network upstreams (`testnet-bridge` / `mainnet-bridge`). The bridge
> compose gives its single local bridge both names as network **aliases**, so
> the default `config.js` (testnet) works as-is — locally, every network
> routes to the same bridge.

## 3. Browser flow

1. Open **`http://localhost:3000`** — exactly this origin: the client's
   registered redirect URI is an exact match, so `127.0.0.1` will be rejected.
2. Click **Sign in with OpenBao** → you land in the OpenBao web UI.
3. Method **Username**, sign in as `testuser` / `testpassword`.
4. OpenBao redirects to `sso-callback.html`, which exchanges the code with
   OpenBao (PKCE, no secret), posts the id token to
   `POST /auth/sso/openbao`, stores the returned bridge JWTs, and lands on
   the dashboard.

Verify the auto-provisioned account:

```bash
docker compose -f impala-bridge/docker-compose.yml exec postgres \
  psql -U postgres -d impala -c \
  "SELECT a.payala_account_id, a.profile_source, au.auth_provider
     FROM impala_account a JOIN impala_auth au ON au.account_id = a.payala_account_id
    WHERE a.payala_account_id = 'testuser@example.com';"
```

## 4. Troubleshooting

- **OpenBao restarted → SSO breaks.** Dev mode is in-memory: a restart wipes
  the IdP config and the *generated client_id changes*. Recreate the stack
  (`just down && just up`) so `openbao-init` re-runs **and** the bridge
  restarts with the fresh `/bootstrap/sso-config.json`.
- **Button missing.** `curl http://localhost:8080/auth/sso/openbao/config` —
  if `enabled: false`, the bridge started before/without the config file;
  check `openbao-init` logs and restart the `impala-bridge` service.
- **Token exchange blocked in the browser console.** CSP `connect-src` must
  include `http://localhost:8200` (it does in the shipped `nginx.conf`), and
  OpenBao CORS must be enabled (done by `openbao-init`).
- **Admin role.** The first account ever created is bootstrapped to `admin`
  by the DB trigger (`migrations/023_add_account_role.sql`). On an existing
  database, grant it via `ADMIN_ACCOUNT_IDS=testuser@example.com` on the
  bridge instead.
