# Cross-area contract addendum (BINDING — overrides any conflicting sentence in spec-card.md / spec-bridge.md / spec-soroban.md / spec-docs.md)

Decided by the lead after reading all four specs. Where a spec and this addendum disagree, this addendum wins.

## A. Card ⇄ bridge wire formats: the CARD spec's formats are the truth (spec-card.md §3). The bridge adopts them verbatim.
1. CERT message = **114 bytes**: `"IMPALA-CERT:"(12) ‖ CERT_VERSION 0x01 ‖ programId(16) ‖ accountId(16, RFC-4122 BE) ‖ currency(4) ‖ cardPubKey(65, 04‖X‖Y)`. The bridge spec's 97-byte certificate (`card_cert_message(account, tag, pubkey)`) is REPLACED by `card_cert_message(program_id: &[u8;16], account: &Uuid, tag: [u8;4], pubkey: &[u8;65]) -> [u8;114]`. `cert_id = SHA-256(CERT)`.
2. XFER message = **89 bytes**: `"IMPALA-XFER:"(12) ‖ TRANSFER_PROTOCOL_VERSION 0x01 ‖ programId(16) ‖ signable(60)`. EVERY transfer signature the bridge produces (issuance credits) or verifies (redemptions) is ECDSA-P256/SHA-256 over the 89-byte XFER message — never over the bare 60 bytes. The bridge spec's "sign raw 60 bytes / format_version=1 untagged" is REPLACED: `format_version = 1` MEANS the tagged 89-byte v1 message (the untagged envelope is retired and must be refused: a signature that verifies only over the bare 60 bytes is invalid).
3. `transfer_id = SHA-256(XFER message)` is THE canonical id of a card transfer. The bridge's `offline_redemption.signable_hash` column is renamed `transfer_id CHAR(64) NOT NULL UNIQUE` and holds sha256 of the 89-byte XFER (not of the 60-byte signable). Dedupe anchors for redemption: `UNIQUE(card_id, sender_counter)` AND `UNIQUE(transfer_id)`.
4. `dateTime` is a per-sender **send sequence**, not a timestamp (spec-card.md §3.2). The bridge MUST NOT enforce age/skew on it: drop `REDEMPTION_MAX_AGE_SECS` / `REDEMPTION_MAX_FUTURE_SKEW_SECS`; store it as `send_sequence BIGINT` for audit (rename `signed_at` semantics accordingly, or keep the column name with a comment; either way no freshness check). Replay protection is the counter rule + `transfer_id` uniqueness.
5. Counter jump bound is shared: `CARD_RECEIVE_COUNTER_MAX_JUMP = 1024` (card spec §6.1 `J`). Any bridge `counter_max_jump` policy value is a constant 1024 (or a column with `CHECK (counter_max_jump BETWEEN 1 AND 1024)` defaulting to 1024). The issuance counter allocator (`counter = max(last, observed)+1`) and the redemption counter rule use it.
6. Currency tag table (bridge `CARD_CURRENCY_TAGS`): `("XLM", b"XLM\0")`, `("USDC", b"USDC")`, `("USDT0", b"UST0")`. The card treats currency as opaque 4 bytes; the SDK exposes helpers for the same three tags (`TransferProtocol.kt`).
7. programId: **bridge-generated**, 16 random bytes (UUIDv4 bytes), created in the same transaction as the FIRST issuer key (`offline_policy.program_id BYTEA(16)`), never changes on issuer-key rotation. Exposed as `program_id_hex` in `GET /card-issuer` (public), in `POST /admin/card-issuer/generate`'s response, and in `POST /admin/cards/{card_id}/certificate`'s response together with `cert_message_hex` (114 bytes). A terminal personalizes a card with `PERSONALIZE` A (accountId, currency, programId, initialReceiveCounter), B (issuer pubkey from `GET /card-issuer`), C (the DER certificate from the certify endpoint).
8. Certificates are bridge-issued only (`POST /admin/cards/{card_id}/certificate`, `Privileged<ManageKeys>`). `POST /card` does NOT accept client-supplied certificates/program ids (the card spec's "bridge follow-up" for `POST /card` fields is superseded by the certify endpoint).
9. Issuance credit tail (bridge → card): `pad72(sig over XFER) ‖ issuer_pubkey(65) ‖ pad72(self_cert)` where `self_cert = issuer.sign(CERT(program_id, redemption_uuid, currency_tag, issuer_pubkey))`, signable `sender = redemption_uuid`, `recipient = card_account_uuid`, `counter` per §5. This MUST satisfy the card's `VERIFY_TRANSFER_V2` checks in spec-card.md §4.10 exactly (sender ≠ me, recipient == me, currency == mine, counter rule, cert over 114 bytes under issuerPubKey, sig over 89 bytes under the tail pubkey).
10. Redemption tuple (card → bridge): `signable_hex(120) + signature_der_hex(≤144) + card_pubkey_hex(130) + card_cert_hex(≤144, the card's issuer certificate as installed by PERSONALIZE C)`; the bridge recomputes CERT(program_id, card_account_uuid, currency_tag(card.currency), card_pubkey) and verifies it under the issuer public key of `card.cert_issuer_version`, then verifies the signature over XFER(program_id, signable). `recipient` must equal `offline_policy.redemption_uuid`.
11. Golden vectors — spec-card.md §3.3 literals are THE shared fixture. Card side: `impala-card/sdk/src/jvmTest/kotlin/com/impala/sdk/TransferProtocolGoldenTest.kt` embeds the four hex literals (CERT 114 B, XFER 89 B, transfer_id, cert_id) and asserts the SDK's builders reproduce them. Bridge side: `impala-bridge/src/handlers/card_auth.rs` tests `golden_xfer_message_layout` / `golden_cert_message_layout` embed the SAME literals (spec-card.md §9.6). `scripts/check-shared-vectors.sh` (created by the bridge PR4 lane; run from both `ci.yml` bridge job and `impala-card.yml` test job) greps each literal in both files and fails if any is missing from either.
12. SW/INS registry is card-owned (spec-card.md §1). The bridge never interprets status words except to record `ack_status_word` as an opaque string.
