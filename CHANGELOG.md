## [Unreleased]

### Added
- **Conversion reserve, second wave: automated replenishment, reserved price quotes, and automated refunds (migration `032_reserve_replenish_quote_refund.sql`).** Each ships behind its own flag defaulting off, and applying 032 changes no behavior until an admin opts in twice (master switch **and** a non-zero cap — 0 means *unconfigured, refuse to run*, never "unlimited").
  - **Automated replenishment.** The pool takes XLM in and pays USDC out, so USDC drained monotonically while XLM accumulated; the USD float only drained. Two independently triggered cycle kinds now sell the accumulated float back: `xlm_to_usdc` through Changelly (fully automatic) and `usdc_to_usd` through OwlPay. Because the bridge can observe USDC leaving and a provider's transfer status but **never a bank credit**, the fiat leg books into `held` as *in transit* and only an admin confirming receipt (`POST .../replenishment/{id}/confirm-fiat`) moves it into `available` — the ledger never claims value nobody verified, and `.../write-off` is the audited escape hatch when it never arrives. Sizing reuses the admin forecast's own math (EWMA, suggested top-up) with treasury entry kinds excluded — load-bearing, because counting the bridge's own inventory moves would inflate the EWMA that sizes the next cycle, so an off-ramp would buy USDC to replace the USDC it deliberately spent. Two price guards (a floor plus a slippage bound against a reference quote) are what stop a mispriced or manipulated quote dumping the float; a chain-aware float guard proves spendability against `min(ledger, on-chain)` and skips rather than spends when Horizon is unreadable; and a cycle never starts while a customer payout may still land, since both sign from one sequence number. "One cycle in flight per kind" is a partial unique index rather than a scan, where `frozen` and `in_transit` deliberately still occupy the slot. Ambiguous sends freeze and are never resubmitted; a definitive rejection unwinds the hold cleanly. Changelly's create has no client idempotency key so an ambiguous create is abandoned (free — an unfunded swap expires), while OwlPay's is safely re-POSTed. The manual `POST .../replenishment/run` takes the watcher's own advisory lock and 409s if it is mid-tick.
  - **Reserved price quotes.** `POST /exchange/quote` with `reserve_lock` now returns a bridge-issued `reserve_quote` (id, locked `amount_to`, expiry) that locks the price **and reserves the capacity behind it**, so an order created with `reserve_quote_id` cannot fail for lack of funds. The capacity is taken once at mint and handed to the order as a zero-delta linkage entry — never released and re-taken, so no racing order can take it and the half-the-pool fraction guard is never re-evaluated against capacity already ours. A quoted order is a commitment: it never falls through to a provider at a different price. The claim is one guarded statement in which every invalid case (unknown, foreign, consumed, expired) collapses to zero rows so quote ids cannot be probed, backed by an order-term match that compares amounts in canonical minor units and payout addresses byte-exactly. A lost response replays to the same order, making `reserve_quote_id` a true idempotency key. Open quotes and open orders share one per-account cap, and the bridge refuses to start if the lock window plus the deposit window exceeds the 7200s ceiling on total price-option exposure.
  - **Automated refunds.** Deposits the reserve cannot use — arriving after expiry, underpaid, or stranded when an admin fails an order — are now returned to their payer instead of waiting on the runbook; `resolve_fail`'s response finally says where the money went. Required capturing the payer for the first time (`from`/`from_muxed` from Horizon, persisted on both the stray-inflow queue and the `deposit` journal entry). Deliberately excluded and left manual, each with a recorded `refund_skip_reason`: unknown-memo inflows (that is how ops tops the pool up — auto-refunding one would wire the float back to ops), wrong-asset inflows, `create_account` funding (the starting balance IS the base reserve), path payments (the payer parted with a different asset), muxed senders (the visible address is a shared base account), and destinations equal to the reserve or to the asset issuer (which would **burn** an issued asset). The claim is a status CAS plus a **write-ahead debit**, so the failure that matters — submitted then crashed — leaves the ledger correct with only metadata missing. Definitive rejections write a compensating reversal and retry; ambiguous outcomes freeze without reversing, because the money may be gone. Admin `reverse` is refused until 600s after the claim and only after verifying on-chain that no matching refund exists. The refund memo is deliberately distinct from an order ref, because `find_onchain_payout` reads that ref as proof a payout landed — a colliding memo would have corrupted both admin resolve actions.
  - **Shared hardening these forced.** One journal INSERT shape for the append-only ledger, widened to carry all five new linkage columns and moved behind a named-field constructor — sqlx does not check bind count at compile time, so a writer that missed a column would have failed at runtime on a money path, and three consecutive `Option<Uuid>` columns would transpose silently. A unified `ORDER_HOLD_SQL` replaces the duplicated hold lookup in `expire_one`/`resolve_fail`, which previously hard-errored when an order's hold was anchored anywhere but its own entry — every quote-backed order that expired or was resolve-failed would have aborted mid-transaction and locked its hold forever. `find_onchain_payout` now also requires the destination to match. `delete_account` additionally refuses accounts holding live price locks or unresolved refunds. Submit classification is extracted and shared, so the payout, refund, and replenishment drivers cannot drift on what counts as definitive. `try_divert_order` gained self-dealing guards so the reserve can never buy from itself.
- **Conversion reserve: a bridge service reserve fulfilling small exchange orders in impala-bridge + admin UI.** Orders under a per-provider threshold ($20–$200, DB-enforced band, admin-set at runtime) are diverted from Changelly/OwlPay to a bridge-owned pool: `changelly_crypto` xlm→usdcxlm swaps are served end-to-end (pay-in to the reserve Stellar account with an order-unique 26-char Crockford-base32 text memo; automatic on-chain USDC payout via the managed-seed signer, which gains issued-asset support), and `owlpay` Stellar-USDC→USD off-ramps divert into an admin fiat-disbursement queue; every miss — shape, threshold, exhausted pool, missing trustline (checked via Horizon before diverting), fixed-rate contracts, quote failure — passes through to the provider unchanged. Reserve orders are ordinary `exchange_order` rows (`provider = 'reserve'`, new row-side vocabulary; the request vocabulary is unchanged so clients can never request it). New migration `031_create_conversion_reserve.sql`: per-currency buckets (BIGINT minor units, USDC/XLM 7 dp + USD cents) with guarded available/held columns, an append-only journal with `UNIQUE(order_id, kind)` idempotency and per-entry balance snapshots, per-provider policies, a durable stray-inflow queue, and a Horizon cursor row. A new deposit watcher (advisory-lock singleton per tick) pages `/accounts/{reserve}/payments?join=transactions` with a monotonic commit-then-advance cursor, matches deposits case-insensitively by memo, credits ACTUAL on-chain amounts, expires unpaid orders only after a fully successful chain scan, and drives payouts through a **write-ahead intent** (`payout_attempt` entry before any submit): definitive Horizon rejections retry bounded, ambiguous outcomes freeze the order `on_hold` and are never resubmitted — admin resolution (`complete`/`fail`) verifies the chain server-side and refuses hold-release while a signed tx could still land. Security: the deposit window doubles as the price-validity window (default 30 min — a long TTL would hand out a free price option on the pool), holds are capped at half the pool plus 3 open orders/account, and the reserve account is quarantined from user-facing `/managed-account/*` endpoints and from account deletion. New admin surface `GET/PUT/POST /admin/exchange-reserve*` (status with live on-chain drift columns, policies, low-water marks, manual topup/withdrawal/adjustment/held_adjustment entries, paginated journal, unmatched queue, disburse/resolve actions — value-moving calls rate-limited 5/min) and `GET /admin/exchange-reserve/forecast`: integer-only utilization prediction (mean + EWMA α=0.3 daily outflow, least-squares trend, projected depletion date, suggested top-up for a target coverage window, per-provider diversion attribution). The admin UI gains a Reserve page (`reserve.html` + DOM-free `reserve-math.js`, vitest-covered): bucket cards with depletion badges, policy editor with client-side $20–$200 validation, hand-rolled SVG utilization chart, work queues, ledger and unmatched browsers. Nine new `reserve.*` outbox event types, `reserve.*` OTel metrics, config `RESERVE_ACCOUNT_ID`/`RESERVE_USDC_ISSUER`/`RESERVE_USDC_CODE`/`RESERVE_DEPOSIT_TTL_SECS`/`RESERVE_WATCH_SECS`, openapi coverage, and runbook `docs/runbooks/conversion-reserve.md`. The exchange reconcile poller now explicitly excludes reserve rows; `transaction.origin` widens to VARCHAR(32) with a `conversion_reserve` origin for payout settlement rows (btxid-linked).
- **`impalactl` — a command-line client for the bridge API.** New top-level Go module (stdlib plus `golang.org/x/term`) that drives the bridge's REST API from a terminal or script: force syncing (`sync force` → `POST /sync`, `sync profile` → `POST /admin/accounts/:id/sync-profile`, `sync payala` → `POST /sync/payala`, `sync mode` → `PUT /admin/accounts/:id/sync-mode`), account creation (`account create`, plus custodial `account generate`/`account import`), transfers (`transfer send` → `POST /managed-account/sign`, `transfer record` → `POST /transaction`), account status (`account show`/`onchain`/`reserves`/`list`), and account activity (`activity list`/`show`/`review`/`events`). Auth mirrors the bridge's own model: `login` stores the refresh/temporal pair `0600` under `$XDG_CONFIG_HOME/impalactl`, **scoped to the issuing endpoint** so a token is never presented to a different deployment, and the single-use refresh rotation is persisted before use and serialized across concurrent invocations with a lock file (a replayed refresh token would otherwise trip the bridge's reuse detection and revoke the whole family). Money-moving calls echo the bridge URL and Stellar network, and require a typed confirmation off testnet — refusing outright when non-interactive unless `--yes` is passed. Secrets (login password, Stellar seed) are read from the environment, a no-echo prompt, or stdin, never from argv; `--json` prints the server's response body verbatim so unmodelled fields survive; exit codes separate usage errors (2) from runtime failures (1). Wire types mirror `impala-bridge/src/models.rs`, and the Payala batch parser rejects unknown fields rather than silently dropping an `amount` or `currency`. Wired into the root `Justfile` as `just test-cli` / `just build-cli`.
- **Exchange integrations: OwlPay Harbor + Changelly (fiat<->USDC on/off-ramp and crypto->USDC swaps) in impala-bridge.** Three optional providers behind new authenticated endpoints `GET /exchange/providers`, `POST /exchange/quote`, `POST /exchange/orders`, `GET /exchange/orders[/:order_id]`: **OwlPay Harbor** (OwlTing) — quote-first v2 transfers for fiat->USDC on-ramp and USDC->fiat off-ramp (`X-API-KEY` auth, idempotency keys, wire `transfer_instructions` surfaced to the caller); **Changelly Exchange API v2** — crypto->crypto swaps such as XLM->USDC-on-Stellar (JSON-RPC 2.0 with RSA-SHA256 request signing over the exact body bytes; float and fixed-rate flows; pay-in address + mandatory memo surfaced); **Changelly Fiat API** — aggregated on/off-ramp offers and hosted-checkout orders (RSA-signed URL+body requests). Orders are recorded in the new `exchange_order` table (migration `029_create_exchange_order.sql`; unified status lifecycle `created/awaiting_deposit/processing/on_hold/completed/failed/refunded/expired` with terminal-status regression guards, provider payload JSONB, optional `btxid` settlement link). The bridge's first *inbound* signature-verified webhooks land at `POST /webhooks/owlpay` (`harbor-signature` HMAC-SHA256 over `{t}.{raw body}` with a 5-minute replay window, constant-time compare) and `POST /webhooks/changelly` (RSA callback signature over the order id; payload treated as untrusted and re-fetched from the API before applying). A new in-process reconcile loop polls non-terminal orders (Changelly's swap API has no webhooks) with the house exponential backoff, and emits `exchange.order_created` / `exchange.order_updated` events into the admin outbox. Provider credentials are read straight from the environment at init (never entering the Debug-logged `Config`); misconfigured credentials fail startup closed. New config: `OWLPAY_API_URL`/`OWLPAY_API_KEY`/`OWLPAY_WEBHOOK_SECRET`, `CHANGELLY_API_URL`/`CHANGELLY_API_KEY`/`CHANGELLY_PRIVATE_KEY[_FILE]`, `CHANGELLY_FIAT_API_URL`/`CHANGELLY_FIAT_API_KEY`/`CHANGELLY_FIAT_PRIVATE_KEY[_FILE]`/`CHANGELLY_FIAT_CALLBACK_PUBLIC_KEY`, `EXCHANGE_POLL_SECS`. Provider-side customer identifiers are bound to local accounts in a new `exchange_customer` table (migration `030_create_exchange_customer.sql`, exclusive in both directions) so an OwlPay transfer can never be executed `on_behalf_of` a customer the caller does not own; webhook endpoints charge unverified requests to a per-source budget and only spend the shared per-provider quota after the signature verifies, so forged traffic cannot lock out genuine deliveries.
- **OpenBao as a local OIDC test IdP for admin-UI SSO.** `docker compose up` / `just up` now bootstraps the local OpenBao dev server as a full OIDC identity provider (userpass login `testuser`/`testpassword`, explicit `impala-admins` assignment, `email`/`profile` scope templates, public PKCE client `impala-admin-ui`, CORS for `http://localhost:3000`) and hands its *generated* client_id to the bridge via a shared-volume `CONFIG_FILE` (`/bootstrap/sso-config.json`), so the whole SSO path — login button → OpenBao web-UI login → PKCE code exchange → `POST /auth/sso/openbao` → auto-provisioned account + bridge JWTs — runs with no external IdP. The SSO registry gains two per-provider keys: `{NAME}_INTERNAL_ISSUER_URL` (server-side base for discovery/JWKS fetches when the public issuer is only browser-reachable; `iss` validation and `GET /auth/sso/:provider/config` keep the public issuer) and `{NAME}_ALLOW_HTTP` (dev-only plain-HTTP opt-in, default off, fail-closed). The admin UI adds the `openbao` provider button and relaxes its token-endpoint check to allow loopback HTTP (new pure `SsoAuth.isAllowedTokenEndpoint`, unit-tested in `tests/sso-auth.test.js`); `nginx.conf` whitelists `http://localhost:8200` in `connect-src`. New runbook `docs/runbooks/test-sso-openbao-local.md`; the multi-provider `SSO_PROVIDERS` scheme is now documented in `impala-bridge/.env.example`.
- **Payala offline-transaction sync (reserve/mirror) in impala-bridge.** Each account gets a `sync_mode` — `reserve` (default) or `mirror` — set by admins via `PUT /admin/accounts/:id/sync-mode` (leaving reserve mode with a nonzero balance requires `force: true`). New `POST /sync/payala` (owner-only, rate-limited) ingests a batch of offline Payala transactions atomically in one Postgres transaction, idempotent per `(account, payala_tx_id)`: **reserve mode** aggregates each batch into a single per-currency net update of the account's reserve balances (new `payala_reserve` table, readable via `GET /reserves/:id`, owner-or-admin); **mirror mode** inserts every fresh item 1:1 into `transaction` (new signed `payala_amount` BIGINT column; `origin = 'payala_sync'`; `source_account` set to the account's Stellar id for owner visibility). Replays are reported as `duplicates` (a replay with a different amount/currency is flagged `conflicting`), and every batch is audited in `payala_sync_batch`/`payala_sync_item` (migration `023_add_payala_sync.sql`). Bookkeeping only — amounts are unverified client assertions and nothing is submitted to Horizon/Soroban. `POST /transaction` is hardened alongside: non-admin callers may only supply a `source_account` they own.
- **Admin console: server-side roles, account management, transaction review, directory sync, and on-chain refresh.** The bridge gains a server-side `role` claim (`view-only`/`device`/`token`/`admin`) embedded in the JWT and enforced via a new `require_admin` guard — the web UI now reads the role from the token instead of browser `localStorage`. New migrations `019_add_account_role.sql` (role column + first-account-admin bootstrap trigger + backfill), `020_add_profile_source.sql` (`profile_source`/`profile_synced_at`), and `021_create_transaction_review.sql` (1:1 review table). New admin-only endpoints `GET /accounts` (paginated/searchable list), `DELETE /admin/accounts/:id` (transactional, with last-admin/self guards), `PUT /admin/accounts/:id/role`, and `POST /admin/accounts/:id/sync-profile` (force LDAP directory re-pull, writing name/affiliation back to `impala_account`). New transaction endpoints `GET /transactions` (admin=all, owner=own via `source_account`↔`stellar_account_id`), `GET /transaction/:btxid`, and `PUT /transaction/:btxid/review` (flag/status/note, admin-only). New `GET /account/onchain` returns live Horizon balances/sequence/signers for this bridge's configured network. `GET /account` is now enriched (role, profile source, stellar id, timestamps) and admins may read/create/update any account. The admin web UI (`impala-ui`) is rebuilt accordingly with a refreshed token-based theme + dark mode, a real account console, server-backed transaction flagging, a force-sync action, and a testnet/mainnet network selector that routes `/api/<network>/*` to the matching bridge deployment (tokens namespaced per network).

### Changed
- Normalized refresh-token TTL references to **14 days** (the value in `impala-bridge/src/constants.rs`) across `impala-bridge/SECURITY.md`, `impala-ui/README.md`, `impala-ui/html/js/api.js`, `impala-ui/html/js/auth.js`, `impala-android-demo/README.md`, `impala-android-demo/.../BridgeApiService.kt`, `impala-android-demo/.../TokenManager.kt`, `impala-android-demo/.../LoginViewModel.kt`. - Replaced the outdated "24 endpoints" label in `ARCHITECTURE.md` with "~30 endpoints" to reflect the actual router.
- **Global HTTP request timeout** of 30 seconds now enforced via `tower::timeout` at the router boundary; any request that exceeds it returns HTTP 408 with a JSON envelope matching the rest of the API.
- **Postgres `statement_timeout`** of 60 seconds is set per connection via a new `after_connect` hook on the sqlx pool, so no single query can wedge a connection indefinitely.
- **Rate limiting expanded** from just `/authenticate` and `/token` to also cover `POST /transaction`, `POST /card`, and `POST /mfa/verify`. Each uses the same 10-requests-per-60-second Redis-backed window keyed by the authenticated user's account id (plus the mfa_type, for MFA verification).
- `tower` dependency pulled in with the `timeout` and `util` features enabled.

### Security
- **IaC hardening (terraform), applied to the primary stack and its DR/testnet clones:** ALBs now set `drop_invalid_header_fields = true`; the SNS jobs topics are encrypted at rest with the AWS-managed SNS key (the CloudWatch-alarm `alerts` topic intentionally stays unencrypted — alarms cannot publish through the AWS-managed key — with a scoped inline ignore); the SQS worker and DLQ queues enable SSE-SQS. Remaining accepted findings are documented in `terraform/.trivyignore`.
- **tfsec → trivy migration** in the pre-commit hook, `security.yml` workflow, and `just scan-tf`: the deprecated tfsec parser rejects the Terraform 1.5 `check` block in `testnet.tf`, so the tfsec gates could never pass; trivy (already used elsewhere in `security.yml`) scans the same config with `--severity HIGH,CRITICAL`.
